# Fusion MAE: multi-process fixes and best-weights restore (2026-10-01)

## Setup

- **Env:** conda env `MultiMAE` (`/root/miniconda3/envs/MultiMAE`): torch 2.11.0+cu130, transformers 5.6.2, accelerate 1.13.0, datasets 4.8.5, timm 1.0.30. The repo is installed editable. Development used the CoSiR env with PYTHONPATH; every number below comes from the MultiMAE env.
- **Hardware:** one RTX 3090, shared with another agent. Multi-process runs used 2 CPU processes with gloo (`torchrun --nproc_per_node 2`, `Accelerator(cpu=True)`, `CUDA_VISIBLE_DEVICES=` so the GPU is hidden).
- **Baseline:** `git archive 27f7e44 | tar -x -C <work dir>/baseline` (27f7e44 = last commit before the 2026-10-01 fixes; pinned in `make_trees.py`, see the fix wave below). Each run passes `--expect-src` and asserts that `src.__file__` resolves to the intended tree. The recorded `code`/`src` field in every JSON confirms it.
- **Ablation trees:** fixed `src/` with exactly one fix reverted, built by `make_trees.py`: `ablate_nofreeze` (fix 2 removed) and `ablate_noprep_test` (fix 3d removed).
- **Data:** real COCO with deterministic strided subsets: 64 train, 32 val, 32 test pairs; 41 val and 43 test retrieval images. `batch_size = eval_batch_size = 16`, 2 epochs, seed 42, `num_workers=2`. 41 and 43 are not divisible by 16 or by 32 (2 × 16), so the last batch is partial on one process and padded with duplicates on the other.
- **Reproduce:** `bash run_all.sh` (sections A to H; it builds the baseline first), then `python compare.py > summary.txt`. Work dir (baseline and ablation trees, checkpoints) defaults to `<this folder>/out/work/` (gitignored with `out/`) and is set with `HARNESS_DIR`; results go to `out/` unless `HARNESS_OUT` is set. `summary.txt` holds the full comparison output. Raw JSON and logs are in `out/`, which the repo's `.gitignore` excludes.

## Problem

The fusion training line (`main_fusion_mmae.py` → `train_fusionmmae_multi_learner`, plus the duplicate `train_fusionmmae`) could not run with more than one process. The best-val weights were also never used for testing. TODO.md tracked the multi-GPU failure as "Multigpu error with eval script".

## Investigation and root causes

1. **Custom methods on the DDP wrapper.** `accelerator.prepare` wraps the model in `DistributedDataParallel` when there is more than one process. The hooks then call `calculate_mae_reconstruction_loss`, `encode_image_tokens_cls` and `encode_text_tokens_cls` on the wrapper, which does not expose them. The baseline under 2 processes fails at the first such call: `AttributeError: 'DistributedDataParallel' object has no attribute 'calculate_mae_reconstruction_loss'` (`train_fusionmmae_multi_learner.py` line 173, `train_fusionmmae.py` line 174).
2. **Unused trainable parameters.** `vision_encoder` and `text_encoder` are used only through `encode_*_clean`, which run under `torch.no_grad()`. Their parameters therefore never get gradients, yet they had `requires_grad=True`. That covers both CLIP backbones and the unused `CLIPMLMEncoder.mlm_head`. With item 1 fixed but these left trainable, DDP (`find_unused_parameters=False`) fails at step 2 with `RuntimeError: Expected to have finished reduction in the prior iteration before starting a new one. This error indicates that your module has parameters that were not used in producing loss.` With `TORCH_DISTRIBUTED_DEBUG=INFO`, DDP names 397 parameters without gradients on rank 0. All 397 sit under `vision_encoder.` or `text_encoder.`, which is exactly the model's 397 encoder parameter tensors, `text_encoder.mlm_head.{weight,bias}` included. `grep` shows `CLIPMAEEncoder` and `CLIPMLMEncoder` are used only by these two model classes. The freeze still lives in the model classes, so `clip.py` is unchanged.
3. **`evalrank` under multiple processes** (`src/hook/eval_fusionmmae.py`):
   - (a) `torch.zeros(...).cuda()` hard-codes CUDA. On CPU it fails with `RuntimeError: No CUDA GPUs are available` (baseline line 273).
   - (b) `encode_data` calls the custom `encode_*_tokens_cls` on the possibly wrapped model, so it fails with `AttributeError: 'DistributedDataParallel' object has no attribute 'encode_image_tokens_cls'`.
   - (c) Embeddings were gathered once, after the loop. By then accelerate has left the dataloader, so `gather_for_metrics` no longer drops the duplicated padding samples. The per-process index maps each started at 0 and were concatenated. With 41 images on 2 processes, the baseline evaluated 64 images (32 per rank, padding included) and its text-to-image map ended in `..., 30, 30, 30, 31, 31, 31, 31, 31]`, so the targets were wrong.
   - (d) The hooks never passed `retrieval_test_loader` through `accelerator.prepare`, so every rank encoded the full test set and the gather duplicated it.
4. **Best weights never restored.** `best_model_state = fusion_model.state_dict().copy()` is a shallow dict copy whose values are the live parameter tensors, so it tracked the current weights. It was also never loaded back, so test numbers always came from the last epoch.
5. **`train.save_dir: None`** in YAML is the string `"None"`. The hooks test `if save_dir:` and wrote checkpoints to `./None/`. `config_check.py` (Hydra compose) prints `baseline: train.save_dir='None' type=str -> hook saves checkpoints: True (into ./None/)`. Checkpoints were also saved from `fusion_model.state_dict()`, which under DDP carries a `module.` prefix on every key (the prepared model's first key is `module.vision_encoder.clip_vision.embeddings.class_embedding`).

**Found along the way (fixed, small):**

6. **Early stopping and best epoch were decided on per-rank val losses.** Each rank averaged only its own shard of `val_loader`, so ranks could disagree on improvement. One rank breaking out of the epoch loop while the other keeps training mismatches the collectives (a hang). Fix 4 makes this matter more, because ranks could otherwise restore different epochs. In the fixed 2-process run, the local val totals differed by rank (epoch 1: 14.400656 on rank 0 vs 14.384943 on rank 1), so the inputs to the decision really do differ.

## Fix

Single-process behaviour is unchanged except for item 4. In a single process, `unwrap_model` returns the same object, `_mean_across_processes` returns its input unchanged, and the frozen parameters had no gradients before either, so AdamW skipped them.

- `src/hook/train_fusionmmae_multi_learner.py` and `src/hook/train_fusionmmae.py` get identical edits, so the two still differ only in the model class.
  - `unwrapped_model = accelerator.unwrap_model(fusion_model)` right after `prepare`. All `calculate_mae_reconstruction_loss` and `encode_*_tokens_cls` calls in train, val and test go through it. `fusion_model(images, token_ids)` still goes through the wrapper, so DDP syncs gradients. (1)
  - `_mean_across_processes()` averages the val epoch losses (total and the three components) over processes in float64, and returns the value unchanged with one process. (6)
  - `_snapshot_state()` takes a CPU clone of the trainable parameters plus buffers from the unwrapped model when val improves, and records `best_epoch`. The frozen CLIP backbones are left out: 99.3 MB per process instead of 770.5 MB for the full state dict. After the epoch loop, `_restore_state()` loads it back (`strict=False`, asserting that only frozen keys are missing) before the test-loss loop and test retrieval. If no epoch ever improved, it prints a message and tests the final weights. `best_epoch` was added to the returned dict. (4)
  - Checkpoints save `unwrapped_model.state_dict()`. (5)
  - `retrieval_test_loader = accelerator.prepare(retrieval_test_loader)`. (3d)
- `src/hook/eval_fusionmmae.py`, `encode_data`:
  - Unwraps the model when an accelerator is given. (3b)
  - Gathers per batch inside the loop with `gather_for_metrics`, keeping captions as `(B, 5, D)` so dim 0 counts samples and the last-batch padding is dropped, then flattens. (3c)
  - Builds `text_to_image_map = arange(N).repeat_interleave(5)` and `image_to_text_map = arange(5N).view(N, 5)` from the gathered count. (3c)
- `src/hook/eval_fusionmmae.py`, `evalrank`: `correct` is created on `inds.device`. (3a)
- `src/model/mmae.py`: in `MultiModalFusionMAE_CLIP` and `MultiModalFusionMAE_CLIP_MultiLearner`, `requires_grad = False` is set on every `vision_encoder` and `text_encoder` parameter right after they are built. (2)
- `configs/fusion_mmae_config.yaml`: `save_dir: null` with a comment. (5)

`main_fusion_mmae.py` needed no change.

## What was not verified

- **Real multi-GPU (NCCL).** Only 2-process CPU/gloo was run, because there is one GPU. On multi-GPU the `.cuda()` in 3a would not crash, since accelerate sets the current device, but items 1, 2, 3b to 3d, 4 and 6 apply unchanged.
- **The hang that fix 6 prevents.** It was not reproduced; only the per-rank disagreement in its inputs was shown.
- **Mixed precision.** Not exercised. The unwrapped custom methods run outside accelerate's autocast wrapper, which is how the single-GPU code already behaved, because there the prepared model was not wrapped.

## Other issues noticed (not changed)

- Under DDP, the train and test epoch averages that get logged are rank 0's shard values; only val is reduced now. The contrastive loss uses the local batch only, as CLAUDE.md already notes.
- Every rank computes the full retrieval metrics: the argsort over (25000 × 5000) plus the Python loops. This costs time but gives correct results.
- The val loss under DDP includes the duplicated padding samples on the last batch, a small bias in the logged value.
- `MultiModalFusionMAE` and `test_eval_fusionmmae.py` are stale (see above).
- CLAUDE.md is now stale in "Fusion MAE architecture" (best state never restored), "Multi-GPU caveats", "Config notes" (`save_dir`) and "Tests" (evalrank needs a GPU because of `.cuda()`). ## Fix wave after final review

1. **Harness reusable.** `make_trees.py` now builds the baseline from the pinned commit `27f7e44` (constant `BASELINE_COMMIT`, last commit before the 2026-10-01 fixes) instead of `HEAD`, so committing the fixes cannot turn the baseline into the fixed code. It asserts that the baseline's `src/hook/eval_fusionmmae.py` still contains `.cuda()` and exits with an error otherwise (checked with a fake baseline lacking it: exit 1, message printed). The hard-coded scratchpad path is gone from `run_all.sh`, `compare.py`, `make_trees.py` and `config_check.py`: they use `HARNESS_DIR` (default `<this folder>/out/work/`, moved under the gitignored `out/` by the controller afterwards), plus `HARNESS_OUT` (default `out/`) in `run_all.sh` and `compare.py`; the repo root is derived from the script location. `run_all.sh` runs `make_trees.py` up front for every section. Verified from a clean work dir with sections `C A`: fingerprint OK; section A (1 GPU, both hooks) reproduces the earlier equivalence (step losses max abs diff 1.91e-06, val and test retrieval identical); section C: baseline crashes under 2 gloo processes for both hooks with `AttributeError: 'DistributedDataParallel' object has no attribute 'calculate_mae_reconstruction_loss'` (exit 1), the fixed code exits 0 with evalrank seeing 41/205, 41/205, 43/215 images/texts, and `fixed_cpu2_multi_best1` tests on the epoch-1 weights. The one-fix-reverted ablation runs exit 1 as intended.
2. **evalrank guard.** `encode_data` raises a `ValueError` when an accelerator runs more than one process and `data_loader` was not prepared. Prepared loaders are `DataLoaderShard` (MRO: `DataLoaderShard, DataLoaderAdapter, DataLoaderStateMixin`) or `DataLoaderDispatcher` (same bases), so the check is `isinstance(data_loader, DataLoaderStateMixin)`. `eval_check.py --unprepared` passes the raw loader. 2 processes, unprepared: ValueError on both ranks. 2 processes, prepared: 41 images, metrics identical to 1 process (r_sum 23.41). No-accelerator path: unchanged (41 images, r_sum 23.41).
3. **`test/epoch`.** Both hooks log `test/epoch` as the 0-based epoch of the tested weights (`best_epoch - 1` if the best weights were restored, else the last epoch). `main_fusion_mmae.py` logs `train/best_epoch` (1-based, with a matching `define_metric`) only when not None, because no epoch may have improved. Verified with `main_fusion_mmae.py` via Hydra on 48-sample COCO subsets, `wandb.enabled=true wandb.mode=disabled`, logger calls captured: `min_delta=1e9` gives best_epoch 1 and `test/epoch` 0.0 (last epoch is 2); `min_delta=1e-4` gives best_epoch 2 and `test/epoch` 1.0; `min_delta=inf` gives no `train/best_epoch` and `test/epoch` 1.0; the plain hook with `min_delta=1e9` gives best_epoch 1 and `test/epoch` 0.0. All exit 0.
4. **`test_mmae_updated.py` exit code.** The failure branch now calls `sys.exit(1)`. `run_small_coco.py` imports the test module, so it never runs the `__main__` block and cannot show the exit code. Verified by running the file with `runpy.run_path(..., run_name="__main__")` under the same dataset subset patch: `image_size=64` gives rc 0, `image_size=32` gives rc 1 (NaN losses). `image_size=64` was restored (file checksum identical before and after).
